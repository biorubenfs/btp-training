BTP en una página

SAP Business Technology Platform es la nube de SAP para construir y ejecutar aplicaciones alrededor de sus productos (S/4HANA, SuccessFactors…). No es un proveedor de infraestructura propio: corre encima de AWS, Azure o Google Cloud y añade una capa de plataforma con servicios de SAP.

Idea clave

En BTP casi todo se reduce a cuatro preguntas: ¿dónde? (jerarquía de cuentas y región), ¿qué puedo usar? (entitlements), ¿qué he creado? (instancias y suscripciones) y ¿quién puede hacer qué? (role collections). Cada sección de estos apuntes responde a una de ellas.

Concepto BTPLo más parecido en AWSMatiz
Cuenta globalAWS OrganizationEl contrato con SAP. Agrupa todo y concentra la facturación.
SubaccountUna cuenta AWS dentro de la OrganizationVive en una sola región. Es la unidad de aislamiento.
Cloud FoundryElastic Beanstalk / HerokuPaaS: subes código y la plataforma lo ejecuta.
Service MarketplaceLa consola de servicios de AWSCatálogo de lo que puedes instanciar.
SAP HANA CloudRDS / AuroraBase de datos gestionada.
XSUAACognitoEmite tokens OAuth2 para apps y servicios.
Role collectionGrupo de políticas IAMSe asigna a usuarios para darles permisos.

Las analogías ayudan a ubicarse, pero no son exactas. Cuando no encajen, gana la definición de BTP.

Analogía

Una empresa (cuenta global) con varias oficinas en distintas ciudades (subaccounts por región). Cada oficina tiene un edificio de Cloud Foundry (org) con varias plantas (spaces). En cada planta trabajan tus apps. Algunas cosas son de la oficina entera, como la base de datos o el control de accesos, y no de una planta concreta.

Ejemplo: cómo se organizaría una empresa

Un patrón habitual en proyectos reales es una subaccount por etapa, porque así cada etapa tiene usuarios, roles y base de datos separados:

Cuenta global "ACME"
├── Subaccount acme-dev   (eu10) → org → space dev
├── Subaccount acme-qa    (eu10) → org → space qa
└── Subaccount acme-prod  (eu10) → org → space prod

En la trial solo hay una subaccount, así que simularemos "producción" con lo que tenemos.

Trampa típica

El cockpit muestra cosas distintas según el nivel en el que estés. Las role collections de la cuenta global (Global Account Administrator/Viewer) no son las de la subaccount (Subaccount Administrator, SAP HANA Cloud Administrator…). Si no encuentras algo, mira la ruta de navegación de arriba: ¿estás en la cuenta global o dentro de la subaccount?

Para recordar
  • Cuenta global ⊃ subaccounts ⊃ una org de CF ⊃ spaces ⊃ apps e instancias.
  • La subaccount es la frontera importante: región, usuarios, roles y servicios.
  • Algunas cosas viven en la subaccount (suscripciones, HANA Cloud) y otras en un space (apps, contenedores HDI).

2Regiones y endpoints

Cada subaccount vive en una región, que es un centro de datos de un hyperscaler operado por SAP. La región se elige al crear la subaccount y no se cambia.

Si lees la URL del endpoint por partes, cada una significa algo:

https://api . cf . us10-001 . hana.ondemand.com
         │     │      │              └─ dominio de SAP BTP
         │     │      └─ landscape (región us10, instalación 001)
         │     └─ entorno Cloud Foundry

Analogía

Como las regiones de AWS (us-east-1), con un endpoint de API por región. La diferencia es que en BTP la región se fija a nivel de subaccount, no de cada recurso.

Para recordar
  • Región → dónde están los datos. Importa para la latencia y para la ley (RGPD → regiones de la UE como eu10).
  • El API endpoint es lo que necesita cf login. Sale de la página de la subaccount.

3Entitlements y cuotas

Un entitlement es el permiso de la cuenta para usar un servicio con un plan concreto. Sin él, el servicio ni siquiera aparece como opción al crear una instancia.

Idea clave

Tu contrato le da a la cuenta global una bolsa de servicios. Esa bolsa se reparte entre subaccounts: entitlement = qué servicio y qué plan; cuota = cuánto (unidades, memoria, número de instancias).

ContratoLa cuenta global tiene derecho a, por ejemplo, 2 unidades de HANA Cloud.
RepartoEl administrador asigna 1 unidad a acme-dev y 1 a acme-prod.
UsoEn cada subaccount ya se puede crear una instancia de HANA Cloud.
Analogía

Un presupuesto por departamentos. La empresa compra licencias y el administrador decide cuántas recibe cada equipo. Un equipo sin licencia de un producto no puede usarlo, aunque la empresa la tenga.

Los entitlements que necesita una app CAP

ServicioPlanPara qué
hana-cloud(el del trial)El servidor de base de datos
hanahdi-sharedUn contenedor HDI (schema) para la app
xsuaaapplicationLogin y autorización de la app
destinationliteGuardar conexiones a sistemas externos

En la trial ya vienen asignados. En una empresa los gestiona el administrador de la cuenta global, y pedirlos suele ser el primer trámite de un proyecto.

Para recordar
  • Entitlement = servicio + plan permitidos en una subaccount.
  • "El servicio no aparece en el Marketplace" casi siempre significa que falta el entitlement.

El entorno es dónde corre tu código. BTP ofrece varios y una subaccount puede activar más de uno.

Analogía

Cloud Foundry es a BTP lo que Heroku a AWS. Tú haces git push (aquí, cf deploy) y te olvidas de servidores, sistemas operativos y balanceadores.

Para recordar
  • CAP + Cloud Foundry es el camino estándar. Kyma es la alternativa con Kubernetes.
  • CF tiene sus propios roles (Space Developer, Org Manager…), además de las role collections de BTP. Lo vemos en la sección 6.

5Servicios, planes e instancias

En BTP casi todo es un servicio del catálogo, y lo que creas a partir de él es una instancia. La misma palabra cubre cosas muy distintas.

Idea clave

Ante cualquier "instancia", pregúntate siempre: ¿instancia de qué servicio y con qué plan?

TérminoQué esAnalogía de programación
ServicioUna oferta del catálogo (Service Marketplace)Una clase
PlanUna variante del servicio: tamaño, precio, funcionesLos parámetros del constructor
Instancia de servicioUn recurso concreto creado para ti, con nombre y credencialesUn objeto: new Destination("lite")

Instancia vs suscripción

Hay dos formas de consumir algo del catálogo. La diferencia importa porque se gestionan de forma distinta:

Instancia de servicioSuscripción
Qué obtienesUn recurso técnico que usan tus appsAcceso a una aplicación SaaS de SAP que usan personas
Cómo se usaCon credenciales (binding o service key)Abriendo una URL en el navegador
Dónde viveNormalmente en un space de CFEn la subaccount
Qué necesitas ademásNada: la app recibe las credencialesUna role collection asignada para poder entrar
Ejemplo en mi trialdest-test (destination / lite)SAP HANA Cloud Central (plan tools)
Analogía

Una instancia es como contratar una base de datos en RDS: te dan host y contraseña y tu código se conecta. Una suscripción es como darte de alta en Jira Cloud: no gestionas nada, entras por URL si tienes permiso.

Ejemplo: lo que hicimos con Destination

Crear instanciaMarketplace → Destination Service → plan lite → space dev → dest-test.
Aparece en CFcf services la muestra, porque vive en el space.
Crear service keyCredenciales para usarla desde fuera (sección 7).
BorrarPrimero la key, después la instancia. No se puede borrar una instancia con keys o bindings vivos.
Para recordar
  • Servicio → plan → instancia, igual que clase → parámetros → objeto.
  • Instancia = para tus apps (credenciales). Suscripción = para personas (URL + role collection).

6Usuarios y roles

Los permisos en BTP se organizan en capas, y cada capa se gestiona en un sitio distinto. Es la parte más confusa al principio.

De la pieza más pequeña a la más grande

ScopeUn permiso atómico definido por una app, por ejemplo Admin. Lo declara el desarrollador.
Role template → RoleAgrupa scopes. La app trae plantillas y BTP crea roles a partir de ellas.
Role collectionAgrupa roles, incluso de apps distintas. Es lo que se asigna a usuarios.
UsuarioRecibe role collections, directamente o a través de grupos del Identity Provider.

Las tres capas de permisos

CapaEjemplosDónde se gestiona
Cuenta globalGlobal Account Administrator, Global Account ViewerCockpit, nivel cuenta global › Seguridad
SubaccountSubaccount Administrator, SAP HANA Cloud Administrator, y las de tus apps (Bookshop_Admin)Cockpit, dentro de la subaccount › Seguridad
Cloud FoundryOrg Manager, Space Developer, Space Manager, AuditorCockpit › org o space › Miembros (no son role collections)
Trampa típica

Ser administrador de la cuenta global no te da permisos automáticos dentro de una subaccount, ni en sus spaces. Cada capa se asigna por separado. En la trial SAP lo hace por ti; en una empresa, el primer día seguramente tendrás que pedir que te añadan.

El patrón que se repite

Suscripción + role collection asignada = puedes usar la app. El booster de HANA Cloud creó la suscripción a HANA Cloud Central y te asignó la role collection SAP HANA Cloud Administrator. Sin lo segundo, al abrirla verías "no autorizado". Con tu propia app CAP pasará lo mismo: declararás un scope Admin, crearás la role collection Bookshop_Admin y te la asignarás (módulo 07).

Para recordar
  • Scope ⊂ role ⊂ role collection → usuario.
  • Tres capas independientes: cuenta global, subaccount y Cloud Foundry.
  • ¿"No autorizado"? Revisa la role collection en la subaccount correcta.

7Bindings y service keys

Una instancia de servicio no sirve de nada si nadie puede llamarla. Hay dos formas de obtener sus credenciales, y las dos dan el mismo JSON.

BindingService key
Para quiénUna app desplegada en CFCualquier cosa fuera de CF: tu portátil, Postman, otro sistema
Cómo llegan las credencialesVariable de entorno VCAP_SERVICES, inyectada al arrancar la appLas copias del cockpit o con cf service-key
Uso en CAPCAP la lee sola en producciónModo híbrido: cds bind (módulo 09)
Analogía

Un binding es como las variables de entorno que Heroku inyecta al añadir un add-on (DATABASE_URL). Una service key es como generar una API key en un panel web para usarla tú desde fuera.

Anatomía de la service key que creamos

Autenticación con id + secreto. La alternativa es x509 (certificados).

Cómo se usan esas credenciales

Todos los servicios de BTP siguen el mismo baile OAuth2 (client credentials):

Pedir tokenEnvías clientid + clientsecret a {url}/oauth/token.
Recibir JWTXSUAA devuelve un access_token firmado, válido unas horas.
Llamar a la APILlamas a {uri}/… con la cabecera Authorization: Bearer <token>.
# 1. Token
curl -u "$CLIENTID:$CLIENTSECRET" \
  -d grant_type=client_credentials \
  "https://7b6c2113trial.authentication.us10.hana.ondemand.com/oauth/token"

# 2. Llamada a la API del servicio Destination
curl -H "Authorization: Bearer $TOKEN" \
  "https://destination-configuration.cfapps.us10.hana.ondemand.com/destination-configuration/v1/subaccountDestinations"

CAP y las librerías de SAP hacen esto por ti, pero conviene saberlo para depurar.

Qué hay en VCAP_SERVICES para el contenedor HDI

Al desplegar, CF inyecta en la app la variable VCAP_SERVICES: un JSON con una entrada por cada servicio bindeado, agrupadas por nombre de servicio. La del contenedor HDI, recortada:

{
  "hana": [{
    "name": "bookshop-db",
    "plan": "hdi-shared",
    "credentials": {
      "host": "xxxx.hana.trial-us10.hanacloud.ondemand.com",
      "port": "443",
      "user": "BOOKSHOP_DB_1_RT",
      "password": "…",
      "schema": "BOOKSHOP_DB_1",
      "certificate": "-----BEGIN CERTIFICATE-----…"
    }
  }]
}

Ahí están el usuario _RT y el esquema de runtime de la sección 8. CAP arranca, busca la entrada de tipo hana y se conecta sin que configures nada. Es la columna "Binding" de la tabla de arriba aplicada a HANA.

Que una app CF llame a otra app CF

Es habitual ver una app que guarda la service key "de otra app" para llamarla. Conviene afinar dos cosas:

  1. Una app no tiene service keys. Solo las instancias de servicio las tienen. Lo que tenía la otra app era una instancia de xsuaa bindeada, y la key se creó de esa instancia.
  2. La key no da acceso a la app, da un token. Contiene clientid, clientsecret y la url de XSUAA. Con eso pides un JWT por client credentials (el diagrama de arriba) y la app destino lo acepta porque lo emitió su propio XSUAA.

Hay tres maneras de montarlo:

FormaCómo llegan las credenciales a la app ACuándo tiene sentido
Service key de la XSUAA de BAlguien la copia a mano en una variable de entorno de AApps de equipos o subaccounts distintos. Es la versión "a mano"
Misma instancia de XSUAA bindeada a A y BYa están en VCAP_SERVICES de A por el bindingA y B van en el mismo mta.yaml. No hace falta key
DestinationA pide el destination por nombre; la librería SAP gestiona el tokenLa forma recomendada. Credenciales fuera del código (módulo de destinations)
 
 A ── clientid/secret (key o binding) ──▶ XSUAA de B ── JWT ──▶ A ── Bearer JWT ──▶ B

La primera opción funciona, pero hereda la trampa de abajo: una credencial real que no caduca y que alguien tiene que rotar.

Trampa típica

Una service key es una credencial real y no caduca sola. Bórrala cuando ya no la uses y no la subas a git (en CAP, cds bind guarda solo una referencia, no el secreto).

Para recordar
  • Binding = credenciales para una app en CF (VCAP_SERVICES). Service key = credenciales para usar fuera.
  • url = dónde pido el token. uri = dónde uso el token.
  • Las apps no tienen service keys, las tienen sus instancias de XSUAA. Para que A llame a B: mismo XSUAA si comparten mta.yaml, destination si no.
  • Orden de borrado: keys y bindings primero, la instancia después.

8SAP HANA Cloud

"Instancia de SAP HANA Database" no es una base de datos de mi app. Es el servidor de base de datos entero, gestionado por SAP. Las apps reciben dentro de él un trozo aislado llamado contenedor HDI.

Las cuatro capas

Hay cuatro palabras que se confunden y conviene separarlas:

TérminoQué es realmenteEquivalente en Postgres
Instancia HANA CloudEl servidor: CPU, memoria, disco. Se crea con el entitlement hana-cloud.Un servidor Postgres en RDS
Base de datosUna sola por instancia. En HANA Cloud no se crean varias.Una única database
EsquemaEspacio de nombres para tablas, como en cualquier SQL. ESQUEMA.TABLA.Un schema
Contenedor HDIDos esquemas + dos usuarios que HDI crea y gestiona como un paquete. Lo pide la app con el servicio hana / hdi-shared.Un schema por app, con grants solo a su owner, automatizado

Un detalle de HANA que cambia la forma de pensar: cada usuario tiene automáticamente un esquema con su mismo nombre. El esquema DBADMIN no es "el contenedor de todo", es solo el esquema personal del administrador y normalmente está vacío. Los contenedores HDI están al mismo nivel que él, no dentro.

Instancia SAP HANA Cloud hana-trialel servidor · vive en la subaccount · servicio hana-cloud · lo creé en HANA Cloud Central
Base de datosuna sola por instancia
esquemas de sistema · SYS, _SYS_BI…
esquema DBADMIN · el personal del admin, normalmente vacío
Contenedor HDI bookshop-dbservicio hana / hdi-shared · vive en el space dev · lo crea HDI como un paquete

usuario BOOKSHOP_DB_1_RT · el que usa la app vía binding
usuario BOOKSHOP_DB_1#OO · owner de los esquemas
Contenedor HDI de otra app(ejemplo)
Sus propios dos esquemas y dos usuarios. Aislado: no ve las tablas de bookshop

Son esquemas normales de HANA. Si entras con DBADMIN al Database Explorer los ves listados junto al resto. La diferencia con un esquema creado a mano es que HDI es su dueño, tú no tienes grants sobre ellos y no debes tocarlos directamente.

Analogía

Un servidor Postgres con una única database, donde cada app tiene su schema y solo su owner tiene permisos sobre él. HDI automatiza ese patrón y lo hace obligatorio. El aislamiento no lo da el esquema en sí, lo dan los permisos atados a los usuarios del contenedor.

¿Qué es HDI exactamente?

HDI (HANA Deployment Infrastructure) es ese paquete de esquemas aislados más un mecanismo de despliegue. No escribes CREATE TABLE: CAP genera ficheros declarativos (.hdbtable, .hdbview…) y HDI calcula y aplica las diferencias contra el esquema #DI. Es como tener un sistema de migraciones dentro de la propia base de datos.

Cómo nace el contenedor al desplegar

Una app CAP necesita como mínimo un contenedor HDI, y las tablas van en su esquema de runtime. Pero nada de eso se crea a mano. En el proyecto solo tocas dos cosas:

  • El modelo, en ficheros .cds: entidades Books, Authors… con sus campos.
  • La dependencia de HANA, en package.json o mta.yaml: una línea que dice "este proyecto usa hana con plan hdi-shared".

A partir de ahí la cadena es automática:

 .cds ──cds build──▶ gen/db/*.hdbtable ──cf deploy──▶ broker hana crea el contenedor
                                                        (2 esquemas + 2 usuarios)
                                                               │
                                                      db deployer (app efímera)
                                                      entra como owner #OO y pasa
                                                      los .hdbtable a HDI
                                                               │
                                                      HDI crea/modifica tablas en
                                                      BOOKSHOP_DB_1 y anota en #DI
                                                               │
                                                      bookshop-srv recibe el usuario
                                                      _RT por binding y empieza a leer
  1. cds build traduce el modelo a ficheros .hdbtable y .hdbview en gen/db.
  2. cf deploy ve que la app necesita una instancia de hana / hdi-shared y la pide al broker. Si no existe, la crea: ahí nacen los esquemas y usuarios.
  3. El db deployer, una app efímera, se conecta con el usuario owner y le pasa los .hdbtable a HDI. HDI calcula las diferencias y las aplica en el esquema de runtime, anotando el estado en el #DI.
  4. La app de servicio recibe las credenciales del usuario _RT por binding y empieza a leer y escribir.

El orden mental es el inverso a "primero creo el contenedor y luego las tablas": describes el modelo, declaras la dependencia, y el contenedor con sus tablas aparece como consecuencia del despliegue. El único paso manual previo es el instance mapping.

Lo que verás en el cockpit

Tras el primer deploy, en el space aparece una instancia de servicio bookshop-db del servicio hana, plan hdi-shared. Esa entrada es el contenedor. Si la borras, se van los esquemas, los usuarios y los datos.

El instance mapping

El servidor HANA vive en la subaccount, pero los contenedores HDI se piden desde un space de Cloud Foundry. El mapping conecta los dos: le dice al broker hana de una org (y opcionalmente de un space) "crea los contenedores en esta instancia".

Instancia HANA "hana-trial"  ──mapping──▶  org 7b6c2113trial / space dev
                                             └─ aquí ya se pueden crear contenedores HDI
Trampas típicas

1. Sin mapping, el despliegue falla al crear el contenedor HDI ("no HANA database found"). 2. En la trial la instancia se para cada noche: hay que arrancarla en HANA Cloud Central antes de trabajar. 3. Si en conexiones permitidas solo están las IPs de BTP, mi portátil no podrá conectar en modo híbrido. Por eso elegimos "Allow all IP addresses".

Para recordar
  • Instancia HANA Cloud = servidor con una única base de datos (subaccount). Contenedor HDI = dos esquemas + dos usuarios de una app (space).
  • hana-cloud lo pide el admin una vez para el servidor. hana / hdi-shared lo consume cada app al desplegar para tener su contenedor.
  • El esquema DBADMIN es el personal del admin. Los contenedores están a su lado, no dentro.
  • La app nunca usa DBADMIN: usa los usuarios técnicos de su contenedor HDI.
  • "Dos bases de datos" = dos contenedores en la misma instancia.
  • El contenedor y sus tablas los crea el deploy a partir del modelo .cds. Tú no creas nada a mano, salvo el mapping.
  • Mapping a la org/space, "allow all IPs" y arrancarla cada día en la trial.

9Boosters

Un booster es un asistente guiado del cockpit que hace por ti varios pasos de configuración seguidos.

Lo que hace un booster lo podrías hacer a mano: asignar entitlements, crear suscripciones o instancias, crear role collections y asignártelas. El booster no deja nada propio; deja exactamente lo mismo que si lo hubieras hecho tú.

Glosario

Cockpit
La consola web de BTP.
Subaccount
Unidad de aislamiento en una región, con sus usuarios, roles y servicios.
Org / Space
Contenedores de Cloud Foundry: una org por subaccount, varios spaces por org.
Entitlement
Permiso para usar un servicio + plan en una subaccount.
Service instance
Recurso creado a partir de un servicio del catálogo.
Subscription
Acceso a una aplicación SaaS multitenant de SAP.
Binding
Unión app ↔ instancia; inyecta credenciales en VCAP_SERVICES.
Service key
Credenciales de una instancia para usarla fuera de CF.
XSUAA
Servicio de autorización OAuth2 de BTP: emite y valida tokens JWT.
Role collection
Conjunto de roles que se asigna a usuarios.
HANA Cloud
Base de datos gestionada de SAP. La "instancia" es el servidor completo.
HDI container
Schema aislado en HANA, con mecanismo de despliegue, para una app.
Instance mapping
Hace visible una instancia de HANA Cloud a una org/space de CF.
Booster
Asistente del cockpit que automatiza pasos de configuración.
MTA / .mtar
Multi-Target Application: app + servicios descritos en mta.yaml y empaquetados para cf deploy.
